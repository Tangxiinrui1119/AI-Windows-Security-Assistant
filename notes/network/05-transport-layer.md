## 5.1 运输层协议概述

### 5.1.1 进程之间的通信（PDF 2～8页）

运输层位于应用层之下、网络层之上。从面向通信的功能看，它是最高层；从用户功能看，它是最低层。课件体系中，网络边缘主机的协议栈具有运输层；核心路由器转发分组主要使用下三层。

| 层次 | 提供的逻辑通信 | 通信端点 |
|---|---|---|
| 网络层 | 主机之间的逻辑通信 | 主机 |
| 运输层 | 应用进程之间的端到端逻辑通信 | 应用进程 |

运输层屏蔽下面网络核心的细节，使应用进程看到一条端到端逻辑通信信道。**TCP呈现可靠的全双工信道，UDP呈现不可靠信道**，不能把“运输层”一概等同于可靠交付。

**复用**：多个应用进程的数据经运输层交给IP层。**分用**：接收端运输层根据端口等信息，把数据交给相应应用进程。课件图中IP层也有对TCP、UDP的分用，不要与运输层按端口分用混淆。

### 5.1.2 运输层的两个主要协议（PDF 8～10页）

两个对等运输实体间传送的数据单位叫作**运输协议数据单元TPDU**。

| 比较 | UDP：用户数据报协议 | TCP：传输控制协议 |
|---|---|---|
| 英文 | User Datagram Protocol | Transmission Control Protocol |
| 服务 | 无连接 | 面向连接 |
| 可靠性 | 尽最大努力，不保证可靠交付 | 提供可靠交付 |
| 数据单位 | UDP报文 / 用户数据报 | TCP报文段segment |
| 通信方式 | 支持单播、多播、广播 | 点对点单播 |
| 数据组织 | 面向报文，保留边界 | 面向字节流，不保留数据块边界 |
| 首部 | 固定8字节 | 最小20字节 |
| 课件典型应用 | 多媒体；图列DNS、DHCP、RIP等 | 万维网、电子邮件、文件传送；图列HTTP、SMTP、FTP、TELNET等 |

后两项特点分别在5.2、5.3展开。这里的典型应用按课件图归纳，不据此扩展为其他协议版本的完整分类。

### 5.1.3 运输层的端口（PDF 10～17页）

不同操作系统的进程标识符格式不同，进程也会动态创建、撤销；通信双方需要统一、稳定的服务标志，因此采用**协议端口号**。IP地址用于找到对方主机，端口号用于把报文交给该主机的相应应用进程。

| 类型 | 含义 |
|---|---|
| 软件端口 | 协议栈层间的抽象接口，应用进程与运输实体交互的位置 |
| 硬件端口 | 路由器、交换机等设备上的硬件接口 |

本章端口指软件端口。端口号为**16位**，只有**本地意义**：`192.168.1.7:80`与`192.168.10.2:80`分别属于两台主机，不能仅凭端口号80判定为同一个通信端点。

| 课件分类 | 范围 | 用途 |
|---|---|---|
| 服务器端：熟知端口 | 0～1023 | 为众所周知的应用层协议使用，由IANA分配 |
| 服务器端：登记端口 | 1024～49151 | 课件所述需向IANA登记的应用程序端口 |
| 客户端：短暂端口 | 49152～65535 | 客户进程临时选择，通信结束后可再分配 |

以上沿用课件的用途分类。熟知服务端口让客户能找到服务器；客户端不必预先知道自己会被分配哪个短暂端口。

常用熟知端口（PDF 17页）：

| 应用层协议 / 服务 | 端口号 |
|---|---:|
| DNS | 53 |
| TFTP | 69 |
| SNMP | 161 |
| SNMP Trap | 162 |
| SMTP | 25 |
| FTP数据连接 / 控制连接 | 20 / 21 |

## 5.2 用户数据报协议 UDP

### 5.2.1 UDP概述（PDF 18～21页）

UDP只在IP数据报服务之上增加少量功能：**复用与分用、差错检测**。

六个主要特点：

1. **无连接**：发送前无须建立连接，减少开销与发送前时延。
2. **尽最大努力交付**：不保证可靠交付，无须维持复杂连接状态表。
3. **面向报文**：不合并、不拆分应用层报文，保留其边界，一次交付一个完整报文。
4. **没有拥塞控制**：UDP本身不会因网络拥塞自动降低发送速率；课件联系IP电话、视频会议等实时应用。
5. **支持多种交互**：一对一、一对多、多对一、多对多。
6. **首部开销小**：只有8字节。

发送端对一个应用层报文添加UDP首部后交给IP；接收端去掉UDP首部后交付应用进程。图中的UDP逻辑通道不表示建立了连接。

应用程序需要选择合适报文大小：过长可能导致IP分片，过短则首部占比过大，两者都会降低效率。**UDP不拆报文，与下层IP可能分片并不矛盾。**

### 5.2.2 UDP的首部格式（PDF 22～24页）

`UDP用户数据报 = 8字节首部 + 数据字段`。四个字段各占2字节：

| 字段 | 作用 |
|---|---|
| 源端口 | 需要对方回信时使用；课件规定不需要时可全0 |
| 目的端口 | 终点交付报文必须使用 |
| 长度 | 整个UDP用户数据报长度，最小8字节 |
| 检验和 | 检测UDP数据报传输差错；检出差错则丢弃 |

接收端按目的端口分用。检错不等于可靠传输：这里没有因此增加确认和重传。

#### UDP检验和与伪首部

计算时临时拼接：**12字节伪首部 + UDP首部 + 数据**。

| 伪首部字段 | 字节数 | 课件值或含义 |
|---|---:|---|
| 源IP地址 | 4 | 发送方IPv4地址 |
| 目的IP地址 | 4 | 接收方IPv4地址 |
| 全0 | 1 | 0 |
| 协议 | 1 | UDP为17 |
| UDP长度 | 2 | 首部与数据总长度 |

**伪首部仅用于检验和计算，不是UDP的真实首部，也不作为额外字段发送。**

发送端将检验和字段置0，把参与计算的内容按16位分组，进行二进制反码求和，再将结果取反作为检验和。若数据字节数为奇数，计算时在末尾补一个全0字节；该填充用于计算。

课件24页例：源`153.19.8.104`、目的`171.3.14.11`、源端口1087、目的端口13，7字节数据`TESTING`，UDP总长度15；补零参与计算，求和结果`0x96ED`，检验和为`0x6912`。接收端连同收到的检验和检验；按课件的求和后取反表示法，无差错结果为全0，否则丢弃。

## 5.3 传输控制协议 TCP 概述

### 5.3.1 TCP最主要的特点（PDF 25～27页）

TCP在无连接、不可靠的IP服务上增加可靠性措施，主要特点为：

1. **面向连接**。
2. 每条连接**只能有两个端点**，点对点、一对一。
3. 提供**可靠交付**。
4. 提供**全双工通信**。
5. **面向字节流**。

“流”是流入或流出进程的字节序列。应用程序每次可以交给TCP一个数据块，但TCP把它看成无结构的连续字节流。**接收应用读到的数据块大小不必对应发送应用写入的数据块大小，最终字节流应相同。**

TCP不关心应用一次交下来的报文有多长，而按对方窗口值、当前网络拥塞情况决定如何形成报文段；过长的数据块可拆开，较短的数据可等待积累后发送。TCP连接是**虚连接 / 逻辑连接**，不是物理线路。

### 5.3.2 TCP的连接（PDF 28～30页）

TCP把连接作为基本抽象。**连接端点叫作套接字socket或插口**，由IP地址与端口号拼接构成：

```text
socket = (IP地址:端口号)                              （5-1）
例：(192.169.1.20:2028)

TCP连接 = {socket1, socket2}
        = {(IP1:port1), (IP2:port2)}                  （5-2）
```

每条TCP连接由两端的两个套接字唯一确定。端点不是单独的主机、IP地址、进程或端口。同一个IP地址或同一个端口号，可以出现在多条不同TCP连接中。

课件还提醒socket有多种语境：socket API、名为socket的函数、函数创建的端点、返回的socket描述符、内核socket实现。这里讨论连接端点时采用上面的`IP:端口`含义。

## 5.4 可靠传输的工作原理

### 5.4.1 停止等待协议（PDF 31～38页）

理想传输条件是：信道不产生差错，且无论发送多快接收方都来得及处理。实际网络不满足这些条件，需要可靠传输协议。

#### 一、停止等待、差错与超时重传

基本过程：**发送一个分组 → 停止发送，等待确认 → 收到确认后发送下一个**。为便于讨论，课件只画A发送、B接收并确认；全双工双方实际都可承担发送与接收角色。

| 情况 | 接收方B | 发送方A |
|---|---|---|
| 正常收到M1 | 返回ACK1 | 收到确认后发M2 |
| M1出错 | 丢弃，不发确认 | 超时后重传M1 |
| M1丢失 | 不知道有该分组，不作响应 | 超时后重传M1 |
| ACK1丢失 | 收到重复M1时丢弃重复数据，重新确认 | 等待超时后重传 |
| ACK1迟到 | 对重复M1重新确认 | 收到重复确认时丢弃重复确认 |

发送一个分组时设置超时计时器；到期前收到对应确认就撤销计时器，否则重发，直到确认到达。可靠传输所需的四件事：**停止等待、暂存副本、分组与确认编号、超时重传**。重传时间应略大于平均往返时间，避免不必要重传。

**ARQ = Automatic Repeat reQuest，自动重传请求**。这里的“自动”是确认与超时机制自动引起重传，接收方无须另发一个请求重传的报文。

#### 二、信道利用率与流水线

停止等待简单，但信道利用率低。课件公式：

`U = T_D / (T_D + RTT + T_A)`（5-3）

其中`T_D`为数据分组发送时间，`T_A`为确认分组发送时间，RTT为往返时间。RTT远大于`T_D`时，等待占比很高。

**流水线传输**：收到确认前连续发送多个分组，使信道能持续承载数据，提高利用率。连续ARQ与滑动窗口采用这种方式。

### 5.4.2 连续ARQ协议与滑动窗口协议（PDF 39～42页）

发送方维护一个**发送窗口**，窗口内分组可以连续发送，无须逐个停等。收到使已确认范围前进的新确认后，窗口向前滑动。

**累积确认**：接收方对按序到达的最后一个分组确认，表示此前所有分组均已正确收到。41页图中`ACK5`确认M5及之前的分组。这里的分组编号约定与TCP按字节报告“下一个期望序号”的确认号约定不同。

- 优点：容易实现；前面某个确认丢失，仍可能由后续累积确认覆盖，无须因此重传。
- 缺点：不能完整报告已收到的所有分组，尤其不能反映有缺口之后的接收情况。

**Go-Back-N（回退N）**：发送M1～M5，M3丢失，接收方只能确认前两个按序分组；课件连续ARQ模型中，发送方要把M3、M4、M5重新传一次，代价是可能重传已发送过的多个分组。

| 对比 | 停止等待结合ARQ | 连续ARQ |
|---|---|---|
| 确认前可发送 | 一个分组 | 窗口内多个分组 |
| 发送控制 | 逐个停等 | 滑动窗口 |
| 确认 | 单独确认 | 可累积确认 |
| 出错后的重传 | 一个分组 | 课件模型使用回退N |
| 共同机制 | 暂存、编号、确认、超时重传 | 暂存、编号、确认、超时重传 |

**不要把该节Go-Back-N直接当成TCP在所有情形下的重传规则**；5.6还会讲TCP对乱序数据的处理和SACK。

## 5.5 TCP报文段的首部格式（PDF 43～54页）

`TCP报文段 = 首部 + 数据`。固定首部20字节，选项最长40字节，填充后整个首部为4字节整数倍，首部总长度20～60字节。以下字段布局沿用课件的6位保留字段、6个控制标志图。

| 字段 | 长度 | 含义 |
|---|---:|---|
| 源端口、目的端口 | 各2字节 | 运输层与应用层接口，支持复用、分用 |
| 序号seq | 4字节 | 本段所发送数据的第一个字节序号 |
| 确认号ack | 4字节 | 期望收到对方下一个数据字节的序号 |
| 数据偏移 | 4位 | TCP首部长度，单位为32位字，即4字节 |
| 保留 | 6位 | 课件格式规定置0 |
| URG、ACK、PSH、RST、SYN、FIN | 各1位 | 控制标志 |
| 窗口 | 2字节 | 本段发送方作为接收方时，通知对方的接收窗口，单位字节 |
| 检验和 | 2字节 | 检验首部和数据，计算时加入12字节伪首部 |
| 紧急指针 | 2字节 | URG=1时有效；课件解释为本段紧急数据字节数 |
| 选项与填充 | 可变 | 选项最长40字节，填充使首部长度为4字节整数倍 |

### 一、序号与确认号（PDF 44～46页）

TCP对**每一个数据字节**编号，而不是每个报文段编号。课件例：5000字节数据，每段数据最多1000字节，从1001开始编号：

| 报文段 | seq | 数据字节范围 |
|---|---:|---|
| 1 | 1001 | 1001～2000 |
| 2 | 2001 | 2001～3000 |
| 3 | 3001 | 3001～4000 |
| 4 | 4001 | 4001～5000 |
| 5 | 5001 | 5001～6000 |

**确认号ack=N，表示到N-1为止的数据都已正确收到，下一步期望N。**

46页例：收到`seq=501`、数据200字节，范围为501～700；若前面数据已连续收到，应回答`ack=701`。

注意：**大写ACK是1位控制标志，小写ack是确认号字段值**。应写`ACK=1，ack=31`，不能把标志位写成`ACK=31`。

### 二、数据偏移与六个标志（PDF 47～50页）

`TCP首部字节数 = 数据偏移值 × 4`。最小合法值5，对应20字节；最大15，对应60字节。

| 标志 | 课件含义 |
|---|---|
| URG：紧急 | 为1时紧急指针有效，指示紧急数据，应尽快传送 |
| ACK：确认 | 为1时确认号有效；连接建立后传送的报文段均须置1 |
| PSH：推送 | 接收TCP应尽快把数据交给应用进程，无须等缓存填满 |
| RST：复位 | 连接出现严重差错，需要释放连接等复位处理 |
| SYN：同步 | SYN=1、ACK=0为连接请求；SYN=1、ACK=1为连接接受 |
| FIN：终止 | 本端数据已发完，要求释放运输连接 |

### 三、窗口、检验和、紧急指针（PDF 51～53页）

窗口字段是在说：**“我作为接收方，还允许你发送多少数据。”** 比如B向A发报文，其中窗口反映B的接收能力，用来让A设置发送窗口；不是在报告A能接收多少。

TCP检验和计算临时加入12字节IPv4伪首部，字段为源IP、目的IP、0、协议号**6**、TCP总长度。与UDP伪首部结构相近，但协议号和长度含义应对应TCP。

课件把紧急指针解释为本报文段紧急数据的字节数，紧急数据放在数据部分最前面；仅在URG=1时有效。本笔记保留课件模型，不额外展开未讲的实现细节。

### 四、MSS与填充（PDF 53～54页）

**MSS = Maximum Segment Size，最大报文段长度**，此名称在课件中指的是**TCP报文段数据字段的最大长度**，不包含TCP首部。

```text
TCP报文段长度 = TCP首部长度 + 数据字段长度
MSS限制一个报文段的数据字段长度
```

MSS与接收窗口不是同一个概念：前者是单个报文段数据长度的上限，后者控制允许对方发送的数据范围。填充用于使TCP首部长度成为4字节整数倍。

## 5.6 TCP可靠传输的实现

### 5.6.1 以字节为单位的滑动窗口（PDF 55～62页）

TCP使用流水线、滑动窗口、确认和超时重传实现高效可靠传输。**发送窗口、接收窗口以字节为单位**，不能直接套用5.4的分组个数。

#### 一、窗口中有什么？

发送窗口中的字节允许在收到新确认前发送；已发未确认的数据必须暂存，以便重传。按课件56～57页图，整个序号空间可分四类，但**只有中间两类在发送窗口内**：

| 区域 | 是否在当前发送窗口内 | 处理 |
|---|---|---|
| 已发送且已确认 | 否，在后沿之前 | 已完成确认 |
| 已发送但尚未确认 | 是 | 保留副本，必要时重传 |
| 允许发送但尚未发送 | 是 | 属于可用窗口 |
| 当前不允许发送 | 否，在前沿之后 | 等待窗口前移等条件 |

#### 二、P1、P2、P3与可用窗口

以窗口`[P1,P3)`表示，右端不包含P3：

- P1：窗口后沿，指向最早未确认字节。
- P2：当前发送位置，指向下一个尚未发送的字节；不是最后已发送字节本身。
- P3：窗口前沿，指向当前窗口范围之外的下一个字节。

```text
P3 - P1 = 发送窗口大小
P2 - P1 = 已发送但未确认的字节数
P3 - P2 = 允许发送但未发送的字节数，即可用窗口
```

57页例：窗口允许31～50，共20字节；已发31～41，共11字节。因此`P1=31，P2=42，P3=51`，可用窗口9字节，对应42～50。

#### 三、接收窗口与窗口滑动

接收方只允许接收窗口内的数据。课件说明，对失序数据的具体处理未作统一规定，通常先暂存，等缺口补齐后按序交付。

57～60页例：B缺31，但已收到32、33，仍回答`ACK=1，ack=31，窗口=20`。31到达后，连续收到的范围扩至33，可回答`ack=34`；A收到该新确认，后沿前移。窗口值保持20时，允许范围由31～50移为34～53。

**可用窗口为0不等于收到零窗口通知**：它也可能表示发送窗口已被未确认数据占满。61页图中发送窗口仍为20，但A暂时不能发送新的数据。

#### 四、缓存、窗口与累积确认

| 缓存 | 暂存内容 |
|---|---|
| 发送缓存 | 应用交给TCP、准备发送的数据；已发送但尚未确认的数据 |
| 接收缓存 | 按序到达但应用尚未读取的数据；暂存的失序数据 |

发送窗口通常只是发送缓存的一部分。接收应用读取过慢会填满缓存，使接收窗口减为0；及时读取可增大接收窗口，但不能超过接收缓存大小。

62页强调：

1. 发送窗口根据接收窗口设置，但由于通知有时间滞后，同一时刻两者**不一定一样大**。
2. 失序数据通常暂存，补齐后再按序交付。
3. TCP接收方必须具有累积确认功能。可以择时确认或捎带确认，但不应过分推迟，以免引起不必要重传。

### 5.6.2 超时重传时间的选择（PDF 63～66页）

**RTT**是报文段发送至对应确认到达的往返时间；**RTO**是超时重传时间。RTO太短会造成不必要重传、增大负荷；太长会增大空闲等待、降低效率。互联网路径与时延变化大，TCP采用自适应算法。

课件公式（64页）：

```text
首次：RTT_S = RTT样本
新的RTT_S = (1 - α) × 旧的RTT_S + α × 新的RTT样本       （5-4）
0 ≤ α < 1，推荐α = 1/8 = 0.125

首次：RTT_D = 0.5 × RTT样本
新的RTT_D = (1 - β) × 旧的RTT_D
          + β × |RTT_S - 新的RTT样本|                  （5-6）
推荐β = 1/4 = 0.25

RTO = RTT_S + 4 × RTT_D                              （5-5）
```

`RTT_S`是平滑的加权平均往返时间；`RTT_D`是RTT偏差的加权平均值。α趋近0时更新慢，趋近1时更新快。上式按课件记号保留，课件未进一步说明公式间的实现更新顺序，不把额外实现规则写作PPT结论。

#### Karn算法及其修正

报文段发生重传后，一个ACK可能对应原报文，也可能对应重传报文，RTT测量存在歧义。因此**不采用已重传报文段的RTT样本**。

若时延突然变大，一直丢弃重传样本又会使RTO无法及时更新。课件修正方法：

`新的RTO = γ × 旧的RTO`，γ典型值为2，即每重传一次就把RTO扩大一倍。以后不再重传时，再按有效往返时间样本更新RTT与RTO。

### 5.6.3 选择确认 SACK（PDF 66～67页）

累积确认只能报告连续接收范围，不能完整告诉发送方“缺口之后哪些数据已经收到”。**SACK = Selective ACK，选择确认**，用TCP选项报告已收到的不连续字节块，帮助发送方仅重传缺失数据。

使用要求：在建立连接时通过允许SACK选项事先协商。**原确认号的累积确认含义不变**；SACK只是额外报告字节块边界。课件选项格式最多报告4个字节块。

| 67页例 | 左边界 | 右边界 |
|---|---:|---:|
| 已连续收到1～1000 | 累积确认号ack=1001 | 不另算作后续不连续块 |
| 字节块1501～3000 | 1501 | 3001 |
| 字节块3501～4500 | 3501 | 4501 |

**左边界是该块第一个字节序号，右边界是最后一个字节序号加1**。例中SACK选项长度18字节。课件图把第二块右边界也标成R1，按块次序应理解为R2，数值仍为4501。

## 5.7 TCP的流量控制

### 5.7.1 利用滑动窗口实现流量控制（PDF 68～70页）

**流量控制**：让发送速率不要太快，使接收方来得及接收。接收方通过首部窗口字段通知接收窗口`rwnd`，发送方据此控制发送范围。

69页例中MSS=100字节，B初始通知rwnd=400。后续通知应结合确认号一起读：

| B给A的通知 | 允许的数据序号范围 |
|---|---|
| ack=201，rwnd=300 | 201～500 |
| ack=501，rwnd=100 | 501～600 |
| ack=601，rwnd=0 | 暂时不允许发送新的数据 |

理解提示：`ack=N，rwnd=W`对应允许范围从N开始，共W字节；若其中一部分已经发出，剩余可用窗口要扣掉已发未确认部分，不能把W全当作还能再发的字节数。

#### 零窗口、死锁与持续计时器

B通知零窗口后，A暂停发送新数据。若B后来发送`ack=601，rwnd=400`的窗口恢复通知却丢失，A等待非零通知，B等待A发送，就可能死锁。

**持续计时器persistence timer**的处理：

1. 收到对方零窗口通知，启动持续计时器。
2. 到期发送**零窗口探测报文段**，按课件携带1字节数据。
3. 对方确认探测时报告当前窗口。
4. 仍为0则重新设置计时器；非0则打破等待，恢复发送。

持续计时器用于处理零窗口通知问题，与5.6的超时重传计时器用途不同。

### 5.7.2 TCP的传输效率（PDF 70～72页）

课件列出控制发送时机的三种机制：

1. 缓存数据达到MSS，组成报文段发送。
2. 发送应用通过推送push操作要求发送。
3. 发送方计时器到期，把已有缓存数据组成报文段发送，长度不超过MSS。

#### 糊涂窗口综合症

每次只传1字节或很少数据会使有效数据占比很低。71页基本首部例：IP首部20字节、TCP首部20字节、数据1字节，总长41字节，效率`1/41≈2.44%`。

| 情况 | 原因 | 课件解决思路 |
|---|---|---|
| 发送方糊涂窗口 | 每收到应用的1字节就立即组成报文发送 | Nagle算法，适当积累数据 |
| 接收方糊涂窗口 | 应用每次只读取少量数据，接收方立即通告很小的新增空间 | 等空间足够后再通知窗口 |

**Nagle算法按71页流程理解**：先发送第1个数据字节；等待时若收到确认，就发送缓存中的数据；若积累数据已达发送窗口一半或达到最大报文段长度，也立即发送。不要机械地把所有零碎数据各发一段。

接收方可等到**空闲空间足以容纳一个最长报文段，或者接收缓存已有一半空闲**时再通知当前窗口。发送方与接收方的措施可配合使用。

## 5.8 TCP的拥塞控制

### 5.8.1 拥塞控制的一般原理（PDF 73～78页）

一段时间内，对某资源的需求超过可用部分，网络性能会明显变坏，输入负荷继续增大时吞吐量反而下降，这叫**拥塞congestion**。

课件条件：`∑对资源需求 > 可用资源`（5-7）。表现包括丢包、时延增大、吞吐量下降，最坏可导致系统崩溃。原因包括缓存太小、链路容量不足、处理机太慢，以及拥塞引起的重传进一步加重拥塞。

单独增加一种资源不一定消除拥塞：只扩缓存可能延长排队并引发重传，只提高处理速度可能把瓶颈移到别处。课件强调丢包是拥塞的**征兆**，不应把“丢包”简单当成拥塞的起因。

| 比较 | 流量控制 | 拥塞控制 |
|---|---|---|
| 目的 | 使接收方来得及接收 | 防止过多数据注入网络，避免路由器、链路过载 |
| 关注对象 | 接收端处理能力 | 整个网络的资源与负荷 |
| 范围 | 点对点通信量、端到端问题 | 全局性过程 |
| 主要联系 | rwnd | cwnd及网络反馈 |

**开环控制**是在设计时预先避免拥塞，运行后不按反馈中途修正。**闭环控制**依据当前网络状态反馈调整，过程为：**监测 → 传送拥塞信息 → 调整**。

监测指标包括缓存不足丢包比例、平均队列长度、超时重传数、平均时延及其标准差等；信息可传回源站、在转发分组中标记，或利用探测分组。调整过频会振荡，过迟则失去作用。

### 5.8.2 TCP的拥塞控制方法（PDF 79～94页）

TCP采用基于滑动窗口的闭环拥塞控制。发送方维护动态的**拥塞窗口cwnd**：无拥塞时可增大，有拥塞或拥塞征兆时应减小。

#### 一、rwnd与cwnd共同限制发送

**发送窗口上限 = min(rwnd, cwnd)**（5-9）

- rwnd较小：接收方能力限制发送。
- cwnd较小：网络拥塞状况限制发送。
- 实际还能发多少新数据，还要看已发未确认数据占用了多少窗口。

80页列出隐式反馈：**重传计时器超时**表示发送方判断已拥塞；**收到三个重复确认**预示可能拥塞。94页同时提醒，路由器处理过久也可能引起超时，发送方的拥塞判断不等于对实际原因的绝对证明。

四种算法：**慢开始、拥塞避免、快重传、快恢复**。

#### 二、慢开始与门限（PDF 81～84页）

慢开始由小到大增加cwnd，探测网络负载能力。控制变量为cwnd和**慢开始门限ssthresh**。

81页记载的初始窗口设置：旧标准1～2个MSS，课件所引RFC 5681为2～4个MSS；82页及后续示例另作简化，**假设从1个SMSS开始**。这是课件版本和教学假设，不把它们混写成统一初始值。

每收到对新数据的确认，拥塞窗口增加量为：

`Δcwnd = min(N, SMSS)`（5-8）

其中N是本次新确认的字节数，SMSS是发送方最大报文段数据长度。不能把重复确认也作为新确认无限增窗。

| 传输轮次 | 示例cwnd（单位：报文段） | 发送范围 |
|---|---:|---|
| 1 | 1 | M1 |
| 2 | 2 | M2～M3 |
| 3 | 4 | M4～M7 |
| 4 | 8 | M8～M15 |

课件理想例中每轮约一个RTT，cwnd大致加倍，呈指数增长。“慢”指从小窗口开始，不是增长速度一直很慢。

门限使用规则：cwnd小于ssthresh用慢开始；大于门限用拥塞避免；等于门限时两种都可。后续图例在到达门限时切换到拥塞避免。

#### 三、拥塞避免与超时（PDF 84～90页）

拥塞避免使cwnd**每经过一个RTT增加约1个MSS**，按线性规律增长，而不是每收到一个ACK都加1个MSS。它减少拥塞发生的可能性，不保证绝无拥塞。

以下窗口数值按课件示例的**报文段数量**计。无论处于慢开始还是拥塞避免，若重传计时器超时：

```text
ssthresh = max(cwnd / 2, 2)
cwnd = 1
重新执行慢开始
```

86～90页例：初始ssthresh=16；cwnd由1、2、4、8增至16，随后线性增至24；发生超时后，ssthresh=12、cwnd=1，重新慢开始，达到12后再拥塞避免。

> 课件内部勘误：86～93页重复曲线的“超时”图注写有“执行拥塞避免算法”，与85页规则及89页正文不一致。按这两处明确说明，应是**超时后执行慢开始**。

#### 四、快重传与快恢复（PDF 91～93页）

**快重传**：接收方即使收到失序报文段，也立即返回重复确认；发送方**连续收到三个重复确认**，立即重传缺失段，无须等到超时。超时计时器仍然保留。

按91页图的缺失情形理解：M1、M2正常，M3丢失，后续M4、M5、M6陆续到达，接收方仍报告期望M3起始字节；这些失序到达可产生三个重复确认，触发重传M3。这里用M编号描述报文段，实际TCP确认号仍是字节序号。

**快恢复**按课件的TCP Reno简化模型：

```text
连续收到三个重复确认
→ ssthresh = 当前cwnd / 2
→ cwnd = ssthresh
→ 执行拥塞避免，线性增长
```

例：cwnd=16时收到三个重复确认，设ssthresh=8、cwnd=8，随后线性增长。与超时后退回cwnd=1、重新慢开始不同。本笔记按PPT模型整理，不扩展其他版本或额外恢复细节。

**AIMD = Additive Increase Multiplicative Decrease，加法增大、乘法减小**：拥塞避免阶段线性增大，出现拥塞征兆后按比例减小窗口。

| 算法 | 使用条件 / 触发 | 核心动作 |
|---|---|---|
| 慢开始 | 小窗口探测、超时后重新开始 | 课件理想例每轮约翻倍 |
| 拥塞避免 | 达到门限后的示例阶段 | 每RTT约增加1个MSS |
| 快重传 | 三个重复确认 | 立即重传缺失段 |
| 快恢复 | 三个重复确认后的课件模型 | 门限减半，cwnd取新门限，再线性增长 |

### 5.8.3 主动队列管理 AQM（PDF 94～99页）

**FIFO**是先进先出规则；**尾部丢弃tail-drop**是在队列已满后，丢弃后续到达分组。二者分别描述排队处理顺序与丢弃策略。

尾部丢弃可能让多个TCP连接同时丢包、超时，进入慢开始，一起降低速率后又一起增长，形成**全局同步global synchronization**。

**AQM = Active Queue Management，主动队列管理**：不等队列完全填满，在达到警惕程度、出现拥塞征兆时就主动丢弃部分到达分组。课件以**RED = Random Early Detection，随机早期检测**为历史示例。

RED依据平均队列长度`L_AV`和两个门限工作，98页的分段表述为：

| 条件 | 丢弃概率p |
|---|---|
| L_AV < Th_min | 0 |
| Th_min ≤ L_AV ≤ Th_max | 处于概率丢弃区间 |
| L_AV > Th_max | 1 |

中间区间p不是常数，课件图示从0逐渐增加到p_max；因此边界处应结合曲线理解，不把整段记成一个固定概率。

**课件历史说明（99页）**：PPT称2015年RFC 7567将RFC 2309列为陈旧，并不再推荐RED，但仍强调AQM必要。本段仅记录此PDF的课程说明，不据此判断当前所有AQM算法的标准化或部署状态。

## 5.9 TCP的运输连接管理

TCP连接有三个阶段：**连接建立 → 数据传送 → 连接释放**。连接管理使建立和释放正常进行。

### 5.9.1 TCP的连接建立（PDF 100～104页）

建立连接要解决：双方确知对方存在；协商参数（如窗口等）；分配运输实体资源（缓存、连接表项目等）。主动发起连接的应用进程是**客户**，被动等待的是**服务器**。

TCP采用**三报文握手（三次握手）**。课件理由是防止已经失效的连接请求报文段又突然到达，造成错误连接。

服务器先创建传输控制块TCB，准备接收请求。正常过程：

| 次序 | 方向 | 字段 | 状态与含义 |
|---|---|---|---|
| 1 | A客户 → B服务器 | SYN=1，seq=x | A主动打开，进入SYN-SENT；B此前为LISTEN |
| 2 | B → A | SYN=1，ACK=1，seq=y，ack=x+1 | B同意连接，进入SYN-RCVD |
| 3 | A → B | ACK=1，seq=x+1，ack=y+1 | A发确认后进入ESTABLISHED；B收到该确认后进入ESTABLISHED |

序号规则：

- 按课件，SYN报文段不携带数据，但**消耗一个序号**。
- 第三次握手的ACK报文段可携带数据；**不携带数据时不消耗序号**。
- 因此若第三次握手不带数据，A下一个数据报文段仍从`seq=x+1`开始。
- 两端进入ESTABLISHED的时机有先后，不能把A发出最后确认与B收到确认当作同一时刻。

> 课件内部勘误：102页把SYN的seq=x描述为“第一个数据字节的序号”，但同页说明SYN消耗序号，103页明确下一数据报文段从x+1开始。因此这里把x称为A的初始序号，后续数据从x+1开始。

### 5.9.2 TCP的连接释放（PDF 105～108页）

TCP全双工，两个方向分别结束。课件正常释放过程采用**四报文握手（四次挥手）**。假设A主动关闭，B被动关闭：

| 次序 | 方向 | 字段 | 状态与含义 |
|---|---|---|---|
| 1 | A → B | FIN=1，seq=u | A不再发送数据，进入FIN-WAIT-1 |
| 2 | B → A | ACK=1，seq=v，ack=u+1 | B进入CLOSE-WAIT；A收到确认后进入FIN-WAIT-2 |
| 3 | B → A | FIN=1，ACK=1，seq=w，ack=u+1 | B也无数据发送，进入LAST-ACK |
| 4 | A → B | ACK=1，seq=u+1，ack=w+1 | A进入TIME-WAIT；B收到最后确认后进入CLOSED |

第2步后是**半关闭half-close**：A到B方向已结束，B仍可向A发送数据，A仍应接收。因此B最终FIN的seq可为w，不必仍等于先前确认报文中的v。

**FIN即使不携带数据，也消耗一个序号**，所以确认u时要回答u+1，确认w时回答w+1。

#### TIME-WAIT与2MSL

A发出最后ACK后不能立即完成本端释放，要等时间等待计时器的**2MSL**后进入CLOSED。MSL为最长报文段寿命（Maximum Segment Lifetime）。

课件108页列出两点理由：

1. 保证发送的最后一个ACK能够到达B。
2. 防止已经失效的连接请求报文段出现在连接中。

应把这段与107页时序图一起记忆：**B收到最后ACK后关闭；A经历TIME-WAIT后关闭**。

#### 保活计时器

课件以长时间空闲的连接为场景：通常设置2小时；服务器超过2小时没收到客户信息就发探测；若连续10个探测报文段、各间隔75秒仍无响应，则假定客户故障，终止连接。这些是**108页给出的参数**，不扩写为所有系统固定启用、固定取值的规则。

### 5.9.3 TCP的有限状态机（PDF 109页）

课件图同时给出正常变迁和异常变迁。先掌握正常路径，再识别同时打开、同时关闭等分支。

| 状态 | 含义 |
|---|---|
| CLOSED | 关闭 |
| LISTEN | 服务器等待连接请求 |
| SYN-SENT | 已发送连接请求 |
| SYN-RCVD | 已收到连接请求并发出SYN和确认 |
| ESTABLISHED | 连接已建立，数据传送 |
| FIN-WAIT-1 | 主动关闭，等待对方确认FIN等事件 |
| FIN-WAIT-2 | 本方FIN已获确认，等待对方FIN |
| CLOSE-WAIT | 已收到对方FIN，等待本地应用关闭 |
| CLOSING | 同时关闭路径中的状态 |
| LAST-ACK | 被动关闭方等待最后确认 |
| TIME-WAIT | 等待2MSL |

正常状态链：

```text
客户建立：CLOSED → SYN-SENT → ESTABLISHED
服务器建立：CLOSED → LISTEN → SYN-RCVD → ESTABLISHED

主动关闭：ESTABLISHED → FIN-WAIT-1 → FIN-WAIT-2
          → TIME-WAIT → CLOSED
被动关闭：ESTABLISHED → CLOSE-WAIT → LAST-ACK → CLOSED
```

图中另有RST、超时、同时打开和同时关闭等分支；以上是课件正常路径，不表示所有连接必经全部状态。
